Open Data Fabric — Apache Ağırlıklı Referans Mimari

Amaç: Microsoft Fabric'teki temel deneyimleri mümkün olduğunca Apache/açık kaynak bileşenlerle karşılayan, on-prem / cloud / hybrid çalışabilen birleşik veri platformu.

1. Üst Seviye Mimari

Platform beş ana katmandan oluşur: erişim ve kimlik, catalog/governance omurgası, data engineering, compute/streaming ve lakehouse. Gravitino, tüm engine'lerin ortak konuştuğu mantıksal omurga; Iceberg ve Ozone ise fiziksel tablo ve depolama katmanını oluşturur.

2. Fabric ile Katman Eşleştirmesi

Microsoft Fabric'teki her deneyimin, bu mimaride yaklaşık bir açık kaynak karşılığı bulunuyor:

  • Fabric Portal / Workspace ≈ Unified Portal + Gravitino Metalake
  • OneLake Catalog ≈ Apache Gravitino
  • Lakehouse ≈ Lakehouse Experience (Gravitino + Iceberg + Ozone)
  • Delta Lake ≈ Apache Iceberg
  • OneLake ≈ Apache Ozone
  • Data Pipeline ≈ Apache NiFi
  • Dataflow Gen2 ≈ Apache Hop Web
  • Notebook ≈ Apache Zeppelin
  • Spark = Apache Spark (birebir aynı)
  • SQL Analytics Endpoint ≈ Trino
  • Semantic Model ≈ Apache Kylin
  • Power BI ≈ Apache Superset
  • Eventstream / RTI ≈ Apache Kafka + Flink
  • Monitoring Hub ≈ Apache SkyWalking

3. Lakehouse İç Yapısı

Gravitino, Bronze/Silver/Gold katmanlarının tümünü kataloglar; her katman Iceberg tablo formatı üzerinden fiziksel olarak Ozone'da saklanır.

4. Kullanıcı Deneyimi — Fabric Benzeri Portal

Workspace içinde kullanıcının göreceği modüller ve arkasındaki Apache karşılıkları:

  • 🗄 Lakehouse → Gravitino + Iceberg + Ozone
  • 🔀 Pipeline → Apache NiFi
  • 🧩 Dataflow → Apache Hop Web
  • 📓 Notebook → Apache Zeppelin + Spark
  • 🧮 SQL → Trino
  • 🔷 Semantic Model → Apache Kylin
  • 📊 Report → Apache Superset
  • ⚡ Real-Time → Apache Kafka + Flink
  • 🧬 Lineage → Apache Atlas
  • 📈 Monitor → Apache SkyWalking

5. Veri Akışı Örneği

Kaynak sistemlerden (SQL Server, PostgreSQL, API, dosyalar) başlayan veri, NiFi ile alınır, Hop ile görsel olarak dönüştürülür, Spark/SQL ile Gold katmana taşınır ve Trino/Kylin üzerinden Superset'e servis edilir.

6. Bileşenlerin Sorumlulukları

Erişim ve platform: Portal (özel geliştirme) tek giriş noktasını; Keycloak kullanıcı/SSO/OIDC yönetimini; Apache Knox güvenli erişimi sağlar.

Catalog ve governance: Apache Gravitino metalake/catalog/metadata omurgasını; Apache Atlas lineage ve classification'ı üstlenir.

Storage ve tablo formatı: Apache Ozone dağıtık fiziksel depolamayı; Apache Iceberg ACID lakehouse tablolarını sağlar.

Data engineering: Apache NiFi veri taşımayı; Apache Hop Web görsel ETL'i; Apache Airflow orchestration'ı; Apache Zeppelin notebook deneyimini karşılar.

Compute ve streaming: Apache Spark büyük ölçekli işlemeyi; Apache Kafka event streaming'i; Apache Flink stateful real-time işlemeyi sağlar.

SQL, semantic ve BI: Trino federated SQL'i; Apache Kylin semantic/OLAP hızlandırmayı; Apache Superset dashboard ve raporlamayı karşılar.

Observability: Apache SkyWalking metrics, log, trace ve alert'leri toplar.

7. Tasarım İlkesi

Gravitino = mantıksal metadata/catalog omurgası
Iceberg = lakehouse tablo katmanı
Ozone = fiziksel veri omurgası
Portal = bütün bileşenleri tek ürün deneyiminde birleştiren katman

8. Fabric'e Göre En Önemli Fark

Microsoft Fabric'te portal, identity, catalog, storage, compute, semantic model ve BI tek yönetilen ürün deneyimi içinde gelir. Bu mimaride teknik motorların büyük bölümü hazır açık kaynak projelerden oluşur; geliştirilmesi gereken temel değer, bu motorları tek workspace, ortak yetkilendirme, ortak metadata ve tutarlı kullanıcı deneyimi altında birleştirmektir.

9. Portal Entegrasyon Modeli — Sürükle-Bırak Deneyimi

Fabric'te kullanıcı Dataflow Gen2'yi tek bir portal içinde, ayrılmadan sürükleyip bırakır. Bu mimaride sürükle-bırak canvas'ları (Apache Hop Web, Apache NiFi) zaten mevcut ama her biri kendi ayrı arayüzünde çalışıyor. Unified Portal henüz özel geliştirme olarak işaretli olduğundan, bu iki canvas'ın Portal'a nasıl bağlanacağı netleştirilmelidir.

Neden sıfırdan native editor önerilmiyor

Bir node-based flow editor'ü sıfırdan geliştirmek; connector şeması, validation, execution engine entegrasyonu, versiyonlama gibi Hop ve NiFi'nin yıllardır olgunlaştırdığı yetenekleri yeniden inşa etmek anlamına gelir. Bu, "asıl değerimiz motorları birleştirmektir" ilkesiyle çelişir.

Önerilen üç fazlı yol

  • Faz 1 — Akıllı embed (düşük efor, baştan itibaren): Hop Web ve NiFi Portal içine iframe olarak gömülür; Keycloak OIDC token'ı ile SSO otomatik geçirilir; navigasyon/tema CSS override ile uyumlulaştırılır.
  • Faz 2 — Mini-builder (orta efor, kullanıcı talebi doğrulanırsa): genel amaçlı editör değil, kısıtlı ve hedefe özel bir sihirbaz (kaynak seç → dönüştür → hedef seç); arkada NiFi/Hop API'sine flow tanımı gönderilir.
  • Faz 3 — Tam native canvas (yüksek efor, yalnızca kanıtlanmış talep varsa): Portal'ın kendi sürükle-bırak editörü, Hop/NiFi API'lerini arkada çağırır.

Sonuç: Fabric'in "tek arayüz" hissi büyük ölçüde entegrasyon kalitesinden gelir, illa tek kod tabanından değil. Faz 1 iyi yapıldığında kullanıcı deneyimi farkı çoğu senaryoda fark edilmeyecek kadar küçülür.

10. Revizyon Notları — Önerilen Alternatifler

Gateway

  • Mevcut öneri: Apache Knox
  • Neden yetersiz kalabilir: Kerberos SPNEGO odaklı; OIDC-only ortamda gereksiz operasyonel yük, her servis için özel topology tanımı gerekir.
  • Önerilen: APISIX / Envoy + OIDC plugin
  • Ne sağlıyor: Keycloak ile doğrudan, deklaratif route tanımı, rate-limiting ve metrics kutudan çıkar.

Lineage

  • Mevcut öneri: Apache Atlas (tek başına)
  • Neden yetersiz kalabilir: Hook'lar Hive/HBase/Kafka kökenli; Spark/Trino/Iceberg için resmi/bakımlı hook yok.
  • Önerilen: OpenLineage → Atlas'a besleme
  • Ne sağlıyor: Spark/Trino/Airflow'da olgun native destek; run-level lineage otomatik toplanır.

Semantic model

  • Mevcut öneri: Apache Kylin
  • Neden yetersiz kalabilir: Kylin bir OLAP pre-aggregation motoru; Power BI Semantic Model'in ilişki/ölçü/DAX katmanına karşılık gelmiyor; Iceberg desteği sürüme bağlı.
  • Önerilen: dbt Semantic Layer / Cube (Kylin'in yanında, yerine değil)
  • Ne sağlıyor: Versiyonlanmış, tek doğruluk kaynağı metrik tanımları; Kylin hesaplama motoru olarak kalabilir.

Observability

  • Mevcut öneri: SkyWalking (her bileşen için)
  • Neden yetersiz kalabilir: Mikroservis/tracing odaklı; Kafka/Spark/Trino/Kylin için olgun plugin seti yok.
  • Önerilen: Prometheus + Grafana + Loki/Tempo (SkyWalking yalnızca Portal için)
  • Ne sağlıyor: Hazır JMX exporter'lar ile sıfır ek geliştirmeyle dashboard.

Metadata omurgası

  • Mevcut öneri: Apache Gravitino
  • Neden yetersiz kalabilir: NiFi/Hop/Zeppelin ile native entegrasyon yok (yalnızca Trino/Spark/Flink olgun).
  • Önerilen: Değişiklik yok — ayrı iş kalemi olarak işaretlenmeli
  • Ne sağlıyor: Gerçekçi efor planlaması.
Not: Trino ve Keycloak Apache Software Foundation projesi değildir; mevcut tasarımda teknik ihtiyaç nedeniyle bilinçli olarak korunmuştur.
